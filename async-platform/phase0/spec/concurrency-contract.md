# Contract: ECS + Deferred Writes — модель конкурентности платформы

Статус: **Phase 0 draft** (проверяется прототипом `../prototype`). ADR #1.
Область: контракт для всех трёх слоёв (ядро → лоадер → моды). Реализация снизу вверх,
проектирование сверху вниз.

Термин **«детерминизм»** здесь = *внутренняя воспроизводимость*: один и тот же вход
(seed + набор систем + порядок) → идентичное финальное состояние мира, независимо от
числа потоков. Это **НЕ** бит-в-бит совпадение с ванильным Minecraft.

---

## 1. Понятия

| Понятие | Что это | Аналог в MC |
|---|---|---|
| **Entity** | Числовой id (row). Данных не хранит. | Блок-энтити, сущность, «тикаемый объект» |
| **Component** | Плоские данные одного типа, хранятся колонкой (SoA). | Инвентарь печи, energy, прогресс, позиция |
| **System** | Логика одного тика над множеством энтити. Объявляет `reads`/`writes`. | «Плавить печи», «тик ИИ», «протолкнуть жидкость» |
| **World** | Колоночное хранилище компонентов + список энтити. | `ServerLevel` состояние |
| **CommandBuffer** | Отложенные *структурные* изменения (create/destroy/add/remove/эффект). | «заспавнить дроп», «поставить блок», «взрыв» |
| **Scheduler** | Из объявленных reads/writes строит **стадии** и запускает их. | Заменяет однопоточный tick-loop |

## 2. Правило конфликта (сердце модели)

Две системы **конфликтуют**, если пересекаются их множества доступа по типу компонента:

```
conflict(A, B) ⇔ (writes[A] ∩ writes[B]) ∪ (writes[A] ∩ reads[B]) ∪ (reads[A] ∩ writes[B]) ≠ ∅
```

- **read ∩ read — НЕ конфликт.** Много систем читают Position одновременно — безопасно.
- Гранулярность — **тип компонента** (консервативно, просто, безопасно). Более тонкая
  (по архетипу / по энтити) — возможная оптимизация позже, НЕ в Phase 0.

Неконфликтующие системы попадают в **одну стадию** и исполняются параллельно.
Конфликтующие — разносятся в **разные стадии** и исполняются последовательно.

## 3. Планировщик → стадии

1. Системы имеют **стабильный порядок** (порядок регистрации / явный priority). Это
   единственный источник недетерминизма, поэтому он фиксирован.
2. Жадная раскладка: идём по системам в стабильном порядке; каждую кладём в самую
   раннюю стадию, где она не конфликтует ни с кем уже там; иначе — новая стадия.
3. Раскладка **детерминирована**: те же reads/writes + тот же порядок → те же стадии.

```
Stage 0: [Thermal(w:Heat), Energy(w:Energy), Progress(w:Progress), Inventory(w:Inv)]  ← параллельно
Stage 1: [Smelt(r:Energy,Heat; w:Progress)]  ← конфликтует с Stage 0, идёт после
```

Внутри стадии — **data-parallel**: работа `(система × чанк энтити)` независима (системы не
конфликтуют, строки энтити различны), диспатчится в общий пул → масштабируется на все ядра.

## 4. Записи: прямые vs отложенные

- **Прямая запись компонента** в свою колонку своих строк — разрешена в параллели, потому
  что правило конфликта гарантирует: никто другой в этой стадии эту колонку не читает и не
  пишет. Гонок нет by construction.
- **Структурные изменения** (create/destroy entity, add/remove component) и **эффекты на
  чужие энтити/блоки** (спавн дропа, взрыв, установка блока) — **нельзя** применять на месте
  во время параллельной фазы. Они пишутся в **CommandBuffer** (thread-local на задачу).

## 5. Apply-фаза (детерминизм + разрешение конфликтов)

После параллельной стадии — **последовательная упорядоченная apply-фаза**:

1. Все команды со всех задач собираются.
2. Сортируются по ключу `(systemOrder, entityId, localSeq)` — тотальный порядок,
   не зависящий от того, какой поток когда закончил.
3. Применяются по порядку. **Write-write на один и тот же таргет разрешается
   детерминированно**: побеждает последняя команда в этом порядке («last-writer-wins
   по расписанию»), либо — по политике компонента — явная ошибка конфликта.

Так достигается и детерминизм, и разрешение write-write без дата-рейсов.

## 6. Контракт для автора мода

Автор пишет **систему**:

```
class SmeltSystem implements GameSystem {
  reads  = {Energy, Heat}
  writes = {Progress}
  void run(view, entity, cmd) {
     int e = view.getEnergy(entity);        // читать можно только объявленное
     view.setProgress(entity, ...);         // писать можно только объявленное
     cmd.spawnItem(pos, stack);             // эффекты — через CommandBuffer
  }
}
```

**Жёсткие правила, проверяемые движком:**
- Читать/писать можно **только объявленные** компоненты. Обращение к необъявленному —
  **hard error** (`ContractViolation`), не проглатывается.
- Никаких прямых `world.setBlock` / прямого доступа к соседним энтити из `run` — только
  через `CommandBuffer`.
- `run` обязана быть чистой относительно необъявленного глобального состояния.

Именно этот контракт даёт безопасную параллельность: планировщик доверяет объявлениям,
а рантайм их валидирует.

## 7. Как это ложится на Minecraft

| MC сейчас (однопоточный tick) | В модели |
|---|---|
| `BlockEntity.tick()` печи | System `Smelt` над компонентами {Furnace, Inventory} |
| `Entity.tick()` / ИИ моба | System `MobAI` над {AI, Position, Path} + эффекты через cmd |
| Block update / редстоун каскад | Команды в CommandBuffer, упорядоченный apply |
| Спавн дропа, взрыв, установка блока | Команды (структурные), НЕ прямая мутация |
| Порядок тиков (детерминированный) | Порядок систем + порядок apply (новый, свой) |

Плотная база (мегафабрика: тысячи печей/хопперов в паре чанков) параллелится, потому что
это **много энтити под немногими системами с непересекающимися write** — ровно тот случай,
где регионы бессильны (всё в одном регионе), а ECS даёт data-parallel по строкам.

## 8. Что НЕ входит в Phase 0

- Реальный ECS-рерайт логики MC (это story `core-rewrite`).
- Генерик-хранилище на архетипах произвольной формы (в прототипе — фикс. колонки).
- Регионы (опциональный поздний слой сверху).
- Тонкая гранулярность конфликтов (per-archetype/per-entity).

## 9. Kill-критерии (когда менять модель)

Прототип **проваливает** ставку и мы пересматриваем модель, если:

1. **Speedup < 1.3×** на плотной сцене при ≥4 ядрах, несмотря на достаточный per-entity
   компьют (т.е. накладные расходы модели съедают выигрыш) — тогда ECS не оправдан.
2. **Неустранимый недетерминизм**: параллельный прогон не воспроизводит reference-состояние
   и расхождение не удаётся ограничить/объяснить порядком apply.
3. **Контракт не валидируется дёшево**: детект необъявленной записи требует затрат,
   сопоставимых с самой работой (тогда «доверяй объявлениям» нежизнеспособен).

Если 1–2 держатся — go на story `core-rewrite`.
