# async-core — детерминированное параллельное ECS-ядро

**Статус: research-прототип.** Это не движок и не мод — это **стенд, который отвечает на один
вопрос**: раскладывается ли реальная логика Minecraft в параллельные детерминированные системы,
и какой с этого speedup. Ответ получен (срезы 1–5, ниже). Кода, пригодного для прода, здесь нет.

Ядро async-native платформы задумано как замена однопоточного tick-loop: вместо «один поток тикает
всё» — **ECS + deferred writes**, где планировщик сам выводит, что можно исполнять параллельно, из
объявленных системами `reads`/`writes`.

## Откуда это взялось

| Фаза | Что делала | Итог |
|---|---|---|
| **Phase 0** | Той-прототип: 150k «машин», 5 систем, целочисленная мешалка | **GO** — 6×/8 ядер, детерминизм бит-в-бит, валидация контракта бесплатна. Но той-модель = *верхняя граница, не прогноз* |
| **story `core-rewrite`** (этот проект) | 5 срезов на реальной логике — по предписанию вердикта: блок-энтити → грязные подсистемы → редстоун | **Модель де-рискована.** Держится на всех трёх классах подсистем |

Вердикт Phase 0 назвал главный непокрытый риск прямо: *«доказан МЕХАНИЗМ, но НЕ доказано, что
реальная логика MC раскладывается в низкоконфликтные системы»*. Срезы 1–5 — это ответ на него.

## Модель за две минуты

- **Entity** — числовой id (строка). Данных не хранит.
- **Component** — плоские данные одного типа, колонкой (SoA → cache-friendly, L3-резидентно).
- **System** — логика одного тика; **объявляет** `reads`/`writes` битовыми масками.
- **Scheduler** — из объявлений строит **стадии**: неконфликтующие системы → одна стадия
  (параллельно), конфликтующие → разные стадии (последовательно).
- **CommandBuffer** — запись в *чужую* строку (хоппер толкает предмет соседу) нельзя делать на
  месте в параллельной фазе → уходит в буфер и применяется в **упорядоченной apply-фазе**.

**Правило конфликта** (сердце модели, `Scheduler.plan`):

```
conflict(A,B) ⇔ (пересечение компонентов) И (пересечение диапазонов строк)
                 writes∩writes ∪ writes∩reads ∪ reads∩writes         Archetype.rangeOverlap
```

`read ∩ read` — **не** конфликт. Per-archetype часть (пересечение строк) добавлена в срезе 2: печь
и хоппер обе трогают `INVENTORY`, но их строки disjoint → в одну стадию (см. RESULTS.md, срез 2).

**«Детерминизм» здесь = внутренняя воспроизводимость:** один вход → идентичное финальное
состояние независимо от числа потоков. Это **НЕ** бит-в-бит совпадение с ванильным Minecraft.
Проверяется как `checksum(reference, 1 поток) == checksum(parallel@8) == checksum(parallel@4)`,
воспроизводимо между прогонами; `DeterminismTest` держит это в CI.

Детерминизм держится на двух вещах: прямые записи идут в disjoint-колонки своих строк (гонок нет
by construction), отложенные — в apply-фазе, отсортированной по `(systemOrder, chunkStart)`, что
не зависит от порядка завершения потоков.

## Что доказано — сводка срезов

Стенд: Ryzen 7800X3D (8 физ. ядер / 16 SMT, 96 МБ L3), JDK Temurin 17, пул = **8 = физ. ядра**
(находка Phase 0: SMT@16 стабильно *хуже*). Замер — JMH: warmup 3×1s, measure 5×1s, fork 1.

| Срез | Сцена | Стадий/проходов | per-entity компьют | speedup@8 |
|---|---|--:|---|--:|
| 1–2 | блок-энтити (чистые r/w) | 1 стадия | лёгкий | **3.14×** |
| 3 | блок-энтити @work=64 | 1 стадия | тяжёлый | **6.89×** (86%) |
| 4 | стая мобов (грязные r/w) | 2 стадии | тяжёлый (соседи) | **5.95×** (74%) |
| 5 | редстоун (ordered-каскад) | 16 проходов | лёгкий | **3.22×** |

**Главный вывод story:** speedup определяет **вес per-entity работы**, а НЕ «грязность» раскладки
и не гранулярность конфликта. Накладные модели (аллокация View/CommandBuffer/задач за тик,
диспатч, apply) фиксированы: на лёгкой работе они доминируют по Амдалу, на реальной — тонут.
Реальная логика MC тяжелее целочисленных заглушек → проекция ближе к 6.9×, чем к 3.14×.

Три частных вывода, которые стоят отдельно:

- **Грязность стоит одной стадии, но окупается.** Мобы читают соседей → +1 стадия, но тяжёлый
  neighbor-компьют дал 5.95×. Логика, которая создаёт грязность, обычно и тяжелее.
- **Ordered-каскад фитится** через double-buffer + fixpoint, не ломая детерминизм.
- **Серийная глубина каскада ограничена дальностью сигнала, не размером мира.** Grid 400×400 =
  160k клеток → fixpoint за **16 проходов**, не ~800: редстоун затухает (15 → 0). Это граница
  модели (каскад ≠ 1 тик), но она не растёт с миром.

Подробности, честная декомпозиция выигрыша и обоснования — **[RESULTS.md](RESULTS.md)**.

## Как собрать и запустить

Требования: **JDK 17** (Temurin; фичи 21 не нужны, toolchain-автопровижен выключен), Gradle —
через wrapper в репозитории, ставить ничего не надо.

```bash
cd async-platform/core
./gradlew demo         # блок-энтити: раскладка по стадиям + чек детерминизма ref==par
./gradlew entityDemo   # грязная стая: раскладка [Sense,Combat]|[Move] + детерминизм
./gradlew redstoneDemo # ordered-каскад: fixpoint ref==par + число проходов
./gradlew test         # 21 тест: детерминизм, контракт (негатив), раскладка, границы
./gradlew jmh          # JMH (Tick+Entity+Redstone) → build/results/jmh/results.txt
```

`demo`-раннеры **бросают** при расхождении checksum — это негатив-контроль, а не печать в лог.

## Карта кода

| Файл | Что |
|---|---|
| `ecs/Scheduler.java` | Планировщик: правило конфликта → стадии, исполнение, apply-фаза |
| `ecs/World.java` | SoA-хранилище (**фикс-колонки** — см. Ограничения), checksum, copy |
| `ecs/View.java` | Доступ системы к миру с **проверкой контракта на каждом обращении** (O(1) битмаска) |
| `ecs/CommandBuffer.java` | Отложенные эффекты в чужие строки + теги для упорядоченного apply |
| `ecs/Components.java` / `Archetype.java` | Id компонентов (биты масок) / архетипы (диапазоны строк) |
| `ecs/systems/` | 7 систем: Furnace/Machine/Hopper, MobSense/Combat/Move, RedstonePropagate |
| `ecs/scene/` | 3 сцены-генератора (детерминированные, seed-based) |
| `ecs/Work.java` | Регулятор веса per-entity работы (диагностика среза 3; вне checksum) |
| `src/test/` | 21 тест | 
| `src/jmh/` | 3 бенчмарка |

Начать чтение: `Scheduler.plan()` (правило конфликта) → `Main.java` (сборка сцены и прогон).

## Текущее состояние и роадмап

Модель конкурентности **де-рискована полностью** — дальше вопрос уже не «работает ли», а
«годится ли хранилище». Не годится:

`World` — research-прототип с **фиксированным набором колонок всех подсистем сразу**: блок-энтити,
сущности и редстоун лежат в одном классе, а `checksum()`, `copy()` и `View` руками перечисляют
каждый компонент. Добавление компонента = правка 4 файлов; класс растёт с каждой подсистемой.

**Следующий шаг — `generalize-archetype-storage`** (крупный): переход фикс-колонки →
generic archetype-based storage (динамические наборы компонентов, разреженные архетипы, добавление
компонента без правки `World`), **сохранив планировщик (range/mask), детерминизм и все бенчи без
регресса**. Числа в таблице выше — и есть «before»-контракт этого рефакторинга.

Отложено осознанно (низкий приоритет, обоснование в RESULTS.md):

- Параллельный swap редстоуна — поднимет 3.22×; серийную глубину 16 не уберёт (принципиально).
- Allocation-reuse View/CommandBuffer между тиками — поднимет только режим work=0.

**Задокументированные dead ends** (не повторять — срез 3 доказал факторным замером, что это
оптимизация НЕ-бутылочного горлышка):

- Расщепление «горячего» `INVENTORY` — раскладка уже 1 стадия, конфликтов нет.
- Распараллеливание apply-фазы — при реальном весе работы она не доминирует.

## Ограничения — что НЕ доказано

Читать обязательно. Числа выше получены на стенде, а не в Minecraft.

1. **Логика — заглушки, а не Minecraft.** Печь/машина/хоппер — целочисленные операции, а не
   настоящие рецепты и маршрутизация. Редстоун — grid-модель затухания 15→0, **без** репитеров,
   компараторов, torch burnout и quasi-connectivity. Мобы — neighbor-сканирование, **без**
   pathfinding/A*. Сцены плотные и однородные; реальный мир разрежен и неоднороден.
2. **Структурные изменения не реализованы и не замерены.** Контракт §1 обещает `CommandBuffer`
   для create/destroy энтити и add/remove компонента — по факту реализованы только отложенные
   эффекты на инвентарь (`OP_ADD`/`OP_SET` по слотам). Спавн дропа, взрыв, установка блока —
   **не покрыты**. Это дыра между контрактом и стендом, а не «мелочь на потом».
3. **Хранилище — фикс-колонки.** Не generic ECS (см. роадмап выше). Разреженные/динамические
   наборы компонентов не поддержаны вообще.
4. **JMH — прод-инструмент, но не глубокое профилирование.** `fork = 1`, одна машина, одна JDK,
   один размер сцены на подсистему. Нет perf-counters, нет alloc-профиля, нет прогонов на другом
   железе и другом числе ядер. Числа — про 7800X3D с 96 МБ L3, где сцена L3-резидентна; на другой
   кэш-иерархии они будут другими.
5. **Ядро в вакууме.** Нет чанков, загрузки/выгрузки, сети, сохранения, модов, интеграции с
   реальным лоадером. Однопоточный tick-loop MC этим ядром **не заменён** — он даже не тронут.
6. **Детерминизм ≠ ванильная совместимость.** Доказана внутренняя воспроизводимость (потоки не
   влияют на результат). Совпадение с поведением ванильного Minecraft не доказано и не заявляется.

Иначе говоря: доказано, что **модель конкурентности жизнеспособна и масштабируется
детерминированно**. Не доказано, что на ней можно запустить Minecraft.
